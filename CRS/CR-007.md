# CR-007: Content inside an expanded section must stay individually lasso-selectable

**Status:** Done

## Request

While a section is expanded, lassoing even a small piece of content
inside the zone instead selects the entire mask/border — the real
content the user wanted to select is never picked, making it
effectively impossible to select anything specific inside an expanded
section. This is a genuine gap: SPEC.md currently says nothing about
lasso-selectability inside an expanded section's zone, even though the
whole point of expanding is to interact with real, editable content
there.

Originated as B-021 (`BUGS/B-021.md`) — full root-cause investigation
already completed there:
- Root cause: the mask fill and border are drawn as `GEO_polygon`
  geometry elements, which appear to be lasso-hit-tested by their full
  bounding box regardless of how little of it is actually visible ink.
  A plain `STROKE` element is hit-tested by its actual rendered pixels
  instead — confirmed on-device (a near-white stroke cloned over real
  content became fully unselectable while the data stayed intact; a
  hand-drawn closed stroke shape did not sweep in content lassoed
  inside it, unlike the current `GEO_polygon`-based mask/border).
- Fix already designed and detailed in `DIAGNOSTIC.md` (to be folded
  into this CR's impact analysis, then removed): rebuild both the mask
  fill and the border using `STROKE` elements instead of `GEO_polygon`,
  same colors/shapes, same visual result.

## Impact analysis

**High impact — escalate to Feature.** This adds a genuinely new,
independently-testable behavioral guarantee not currently in SPEC.md
("content inside an expanded section's zone stays individually
lasso-selectable"), which needs a `REQ-NNN`, Requirements Engineer
drafting, and Quality Auditor review before implementation — that's
the whole reason this was routed through Change Request rather than
staying a bug-investigation fast-track.

The technical design itself is already fully worked out (from B-021's
investigation, folded in here from `DIAGNOSTIC.md`):

**Root cause.** `maskHelpers.ts` draws both the mask fill (concentric
rings faking a solid fill) and the border as `GEO_polygon` geometry
elements. `GEO_polygon` elements are lasso-hit-tested by their full
bounding box regardless of how little of that box is actually painted
ink — so any lasso loop drawn anywhere inside the zone falls within
these elements' bounding boxes and gets swept into the selection.

**Confirmed on-device:**
- A near-white `STROKE` cloned exactly on top of real content became
  completely unselectable by lasso (and invisible), while the
  underlying data stayed intact and readable via `getElements` — not
  destructive, a genuine non-selectable overlay.
- A lasso spanning both that invisible stroke-covered area and a
  separate, real, visible stroke selected only the real stroke.
- A hand-drawn closed stroke shape (a rectangle/circle outline) does
  **not** sweep in content lassoed inside it — only `GEO_polygon` does.

**Fix.** Rebuild both the mask fill and the border in `maskHelpers.ts`
using `STROKE` elements instead of `GEO_polygon` — same colors (fill
stays near-white `0xFE`, border stays black `0x00`), same shapes, same
visual result, only the underlying element type changes.
- Reuse this codebase's own proven `buildStroke` pattern
  (`elementSerializer.ts`) for constructing valid strokes (points,
  `maxX`/`maxY`, ideally pressures) rather than re-deriving it — a
  hand-rolled attempt during the investigation's own diagnostic probe
  failed to render, root cause not fully isolated.
- `createMaskElements`'s ring-stacking math (inset/step sizing) may
  need recalibrating: `GEO_polygon`'s `penWidth` and `STROKE`'s
  `thickness` aren't guaranteed to use the same scale — needs
  on-device visual confirmation the fill still reads as solid/gapless.
- No change needed to deletion (still by `numInPage`) or `userData`
  tagging (`CE_MASK_PREFIX`/`CE_FRAME_PREFIX` work the same on any
  element type).
