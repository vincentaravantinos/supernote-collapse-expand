# CR-008: Bottom-right resize handle for expanded sections

**Status:** Done

## Request

Resizing an expanded section currently only works by dragging the
section's own icon — but the icon sits above-left of the content, and
resizing to grow the area right or downward (the common case for
left-to-right, top-to-bottom writing) means dragging the icon *away*
from the direction the user actually wants to grow, which is
unintuitive. Add a second, dedicated handle at the bottom-right corner
of the expanded area that can also be dragged to resize, as an
alternative to dragging the section's icon (BACKLOG.md item 5).

## Impact analysis

**High impact — escalate to Feature.** This is a genuinely new
interactive affordance, not a mechanical tweak:

- **New persisted, visible element.** The icon's own drag-to-resize
  works because the icon is already a real, persisted page element the
  user can see and grab. A bottom-right handle needs the same: some
  new glyph/marker element, positioned at the expanded area's
  bottom-right corner, created on Expand, repositioned on every resize
  (from either handle), and removed on Recollapse — a new element role
  alongside `CE_PLUG`/`CE_PART`/`CE_MASK`/`CE_FRAME`/`CE_NAME`/
  `CE_UNDERLINE` in the data model table.
- **New hit-testing path.** `onMotionDown`/`onMotionUp` currently
  recognize a drag by checking whether it started near the section's
  *icon* (`expandedEntries()` + `rectContains`). A second draggable
  target needs its own hit-test, distinguishable from the icon's and
  from a normal draw/select gesture.
- **A different resize geometry.** Dragging the icon reshapes the zone
  by stretching *toward* the icon (`stretchZoneToIcon`) while content
  stays fixed. Dragging a bottom-right handle is a different
  operation — the zone's bottom-right corner follows the handle
  directly — which needs its own geometry function, and its own
  answer to the same questions CR-006/B-020/B-022 already had to
  answer for icon-drag resizing (what happens to pre-existing content
  the new corner newly covers, content drawn since Expand, and the
  containment/icon-clearance trade-off from B-022) — likely the same
  rules should apply, but that's a requirements decision, not an
  implementation detail to assume silently.
- **Touches SPEC.md.** At minimum, a new requirement for the handle's
  existence/behavior, and clarification of how REQ-200/210/220/230/240/
  250/260 apply when the resize is triggered by the new handle instead
  of the icon.

## Next step

Done. Implemented as a new persisted `CE_HANDLE:<id>` element (see
DECISIONS.md 2026-09-28) with its own `growZoneToHandle` geometry and
hit-test path, sharing the existing absorb/containment/cleanup logic
with icon-drag resizing. Confirmed on-device (pencil drag); a
finger-drag attempt was investigated as B-024 and found to be the
pre-existing, separately-tracked BACKLOG item 6 gap, not a CR-008 defect.
