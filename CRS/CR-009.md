# CR-009: Finger-drag support for icon/handle resize

**Status:** Done

## Request

BACKLOG.md item 6. Today, resizing an expanded section (by dragging
either the icon or the CR-008 bottom-right handle) only works with the
pencil — a finger touch fires the same motion-listener DOWN/UP sequence
and still triggers the full redraw pipeline (busy popup included), but
the device doesn't relocate a page element under a finger touch, so it
lands as a silent no-op (confirmed via B-024). Requested: either real
finger-drag support (the plugin tracks the finger's own motion delta
and drives the resize itself, since the OS won't move the element for
it), or, at minimum, detecting a finger touch on the icon/handle and
no-op'ing immediately instead of running the expensive redraw for
nothing.

## Impact analysis

**High impact — escalate to Feature.** User chose the full finger-drag
option over the minimal no-op guard. This is a genuinely new
interaction model, not a mechanical fix:

- **No native relocation to react to.** Every existing resize path
  (icon and CR-008's handle) works by letting the pencil-drag actually
  move a real page element, then reading its new position back from
  the page. A finger never moves anything — the plugin has to
  synthesize the intended new position itself from the raw touch
  delta (`up.{x,y} - down.{x,y}`), captured directly in
  `onMotionDown`/`onMotionUp`, and feed that into the existing
  `stretchZoneToIcon`/`growZoneToHandle` geometry in place of a
  freshly-read rect.
- **No live visual feedback is possible.** A per-tick redraw during
  the drag would mean a `modifyElements`/`insertElements` write on
  every `ACTION_MOVE`, at the SDK's documented ~2-3s-per-write floor
  (BACKLOG item 3) — not viable. The resize can only apply once, on
  release, same as the pencil case today — a real UX difference from
  a native drag (no visual tracking mid-gesture) that needs to be
  captured as a requirement, not left implicit.
- **Touches SPEC.md.** At minimum, a requirement stating resize can be
  triggered by a finger drag as well as a pencil drag, and that the
  redrawn result only appears on release (no live feedback) —
  clarifying how this differs from the pencil case's own (already
  instantaneous, since the OS did the moving) experience.
- **Shared code, new trigger source.** `redrawSectionBox` already
  branches on `trigger: 'icon' | 'handle'`; this adds a third case
  (or a finger/pencil orthogonal axis) where `iconRect`/`handleRect`
  come from synthesis instead of a page re-read — needs a design
  decision on how that's threaded through without duplicating the
  downstream absorb/containment/cleanup logic.

## Next step

Done. Implemented via REQ-290/310/320/330/340: the raw down-to-up touch
delta is synthesized into the moved-to rect immediately after it's read
(see DECISIONS.md 2026-09-28), so the existing resize pipeline (zone
geometry, absorb scan, containment clamp) runs unchanged regardless of
whether the position came from a real pencil move or synthesis. A page
re-check immediately before the destructive delete step satisfies
REQ-340. Confirmed on-device: both pencil and finger drags work,
including the existing regression set.
