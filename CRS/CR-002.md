# CR-002: Declare plugin permissions

**Status:** Escalated — Paused

Implementation is done and Part A of validation (permission dialogs,
denial handling, re-ask, message content) has passed. Paused before
completing validation (Part B — Collapse/Expand round trip) because it
uncovered B-016, an external SDK bug (`userData` doesn't survive a round
trip through any read API on this firmware) that is unrelated to this
CR but blocks confirming it end-to-end. Reported to Ratta; resume once
fixed upstream. See `BUGS/B-016.md` and `PLAN.md` for full state.

## Request

The Chauvet 3.29.43/2.26.40 SDK release adds a plugin permission system:
plugins must declare the permissions they need
(`plugin.permission.FILE:READ/WRITE/DELETE/INTERNET`) in
`PluginConfig.json`'s `uses-permissions` array, and request them at
runtime via `PluginManager.hasPermission`/`requestPermission` (which
shows a native OS dialog — "Allow this time only" / "Always allow" /
"Don't allow").

`collapse_expand` currently declares no permissions at all, yet calls:
- read: `PluginFileAPI.getElement`, `getElementNumList`, `getElements`, `getPageSize`
- write/delete: `PluginFileAPI.insertElements`, `modifyElements`, `deleteElements`

Need to determine, confirmed on-device rather than guessed (the SDK docs
are inconsistent about which permission gates which call):
- exactly which permission(s) each call site needs,
- when in the flow to request each one (first collapse? plugin init?
  every launch?), matching the existing UX for each of
  collapse/expand/recollapse/live-redraw/rename,
- what each operation should do on denial (abort before any write,
  where the user is shown how to grant it — mirroring Scribble's
  CR-001 approach).

Source: r/Supernote_dev, "Plugin Preview Build: Chauvet 3.29.43 Beta for
Manta / Nomad and Chauvet 2.26.40 Beta for A5X / A6X" (u/Dunn-sn).

## Impact analysis

**High impact — escalate to Feature.** Multiple design decisions needed
(request timing per operation, denial UX per operation, which permission
actually gates which call needs on-device confirmation via error-code
diagnostics) — this is the same shape as the permission half of
Scribble's own CR-001, except `collapse_expand` has a materially larger
write/delete surface (insert, modify, *and* delete, across five action
modules) than Scribble's read-only erase pipeline had.
