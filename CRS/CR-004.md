# CR-004: Investigate batchUpdatePageElements for dense-page write cost

**Status:** Analyzed

## Request

BACKLOG.md item #3 identifies the per-write-call cost floor
(`insertElements`/`modifyElements`/`deleteElements`/`saveCurrentNote`
each cost ~2-3s regardless of element count) as the main remaining
performance bottleneck on dense pages, and names `replaceElements` as an
untried lever to collapse call *pairs* into one round-trip. The current
code has several such pairs, each today a separate round-trip:
- Collapse: `insertElements` (icon) then `deleteElements` (originals) —
  `collapseAction.ts:136,151`.
- Recollapse: a `modifyElements` write then `deleteElements`
  (parts/mask) — `recollapseAction.ts:173`.
- Rename: `insertElements` then `deleteElements` — `nameAction.ts:162,177`.
- Live icon-drag redraw: a stash write, `deleteElements`, then
  `insertElements` — `iconMoveRedraw.ts:191,250`.

The Chauvet 3.29.43/2.26.40 release adds
`PluginCommAPI.modifyPageElements`/`insertPageElements`/`deletePageElements`/`batchUpdatePageElements`,
a more direct new candidate for the same goal than `replaceElements`.
This CR is to investigate whether they're usable for this and, if so,
how much they'd help — not yet scoped or committed to.

Source: r/Supernote_dev, "Plugin Preview Build: Chauvet 3.29.43 Beta for
Manta / Nomad and Chauvet 2.26.40 Beta for A5X / A6X" (u/Dunn-sn),
Add section.

## Impact analysis

**High impact — escalate to Feature.** Unlike Scribble's analogous
CR-004 (rejected at the analysis stage: their delete step was *already*
a single batched round-trip, so a different batching API couldn't help),
`collapse_expand`'s write pairs above are genuinely separate round-trips
today, so the premise plausibly holds and can't be ruled out by static
reasoning alone — it needs on-device profiling of `batchUpdatePageElements`'s
actual per-call cost and semantics (does it accept mixed insert+delete
in one call? what does partial failure look like?). If adopted, it
touches five action modules and this codebase's crash-safety ordering
guarantees (insert-before-delete, so an interruption mid-operation
leaves the note recoverable) — a real design tradeoff, not a mechanical
swap.
