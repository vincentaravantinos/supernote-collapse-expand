# B-016: Selecting a collapsed icon and pressing the button always Collapses again, never Expands

**Status:** Parked — blocked on an external SDK fix from Ratta.

## Symptom

After a successful Collapse, selecting the resulting "+" icon and
pressing the plugin button does not Expand it — the icon simply gets
"collapsed" again (a new icon nested on top of the first). The
finger-tap shortcut on the same icon also does nothing. No error, no
permission dialog — nothing user-visible beyond the wrong outcome. An
earlier repro in this same investigation showed a 60s watchdog hang
instead of a clean-but-wrong re-collapse; not reconciled, and not worth
chasing further given the root cause below is external and not
something a code change on our side can fix.

## Root cause (confirmed via instrumentation — this is NOT a CR-002/permission bug)

`PluginFileAPI`'s read APIs (`getElements`, `getElement`) and
`PluginCommAPI.getLassoElements` all fail to return `userData` for any
element, of any type, even immediately after that exact element was
written with `userData` via `insertElements`. Confirmed directly:

```
B-016-PROBE classify num=4 type=500 userData=undefined parsedKind=null
B-016-PROBE cross-check num=4 via PluginFileAPI.getElement userData=undefined
```

The second line is a direct `PluginFileAPI.getElement` call on the exact
same element `getLassoElements` had just returned with no `userData` —
also `undefined`. This rules out `getLassoElements` specifically; the
gap is in the SDK's `userData` round-trip generally, on this firmware.

Since `src/index.ts`'s classification logic depends entirely on reading
back an icon's `CE_PLUG:` tag from `userData` to recognize it (as does
every other piece of state this plugin persists — SPEC.md's whole
"Persistence requirements" section is built on `userData` surviving a
round trip), this is not fixable from the plugin's own code. It affects
Collapse/Expand/Recollapse/Rename/live-redraw alike, not just the
Expand path this particular repro exercised.

**This is an already-known, already-documented SDK bug** — an earlier
investigation (this same FEEDBACK.md) had already found and written up
the identical symptom on a different device:

> Bug: on Chauvet 2.26.40 Beta (A5X), `PluginFileAPI.getElements` never
> returns a `userData` value for any element, of any type — it's simply
> absent from the returned object, even immediately after that exact
> element was written with `insertElements`.

This session's device is also A5X/A6X (Chauvet 2.26.40), so this is a
reconfirmation on the same device family, now also covering `getElement`
and `getLassoElements` (the earlier report only covered `getElements`).
