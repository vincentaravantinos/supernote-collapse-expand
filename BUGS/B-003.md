# B-003: Moving icon+name together while collapsed overshoots the name on next Expand

**Status**: Fixed — added `CollapseSection.nameSyncedRect` and a shared
`nameFollowDelta` check (`nameAction.ts`) used by both `expandAction.ts`'s
collapsed-move reconciliation and `iconMoveRedraw.ts`'s live expanded-drag
reconciliation: the name only auto-follows the icon if it hasn't moved on
its own since last synced. Confirmed on-device across all three cases: icon
alone moved (name still follows), name alone moved (name stays put), and
icon+name moved together (both land together, no overshoot).

## Symptom
Section is collapsed and named. User selects both the icon and its name
together and drags them to a new location in one move. On the next Expand,
the icon is correctly at the new location, but the name ends up somewhere
else (not where the user moved it to).

## Hypothesis
`expandAction.ts`'s collapsed-move name-reconciliation always assumes the
name was left behind by a drag that grabbed only the icon (the case the
mechanism was built for): it computes `dx/dy` from the icon's movement
(`iconRectNow - section.iconRect`) and blindly translates the name's
*current* on-page position by that same delta.

That's correct when only the icon moved. But if the user lassoed and moved
the icon **and** the name together, the name has *already* physically moved
by exactly `(dx, dy)` before Expand ever runs. Re-applying `(dx, dy)` on top
of that moves it a second time — landing at
`original_position + 2×(dx, dy)` instead of `original_position + (dx, dy)`,
which reads as "the name jumped somewhere else."

There's no way to distinguish "icon moved alone, name left behind" from
"icon and name moved together" from final positions alone — both leave the
icon at a new spot; only the name's position differs, and we have no record
of where the name *was* to compare against.

## Evidence
None yet — this is inferred from the code and matches the reported
mechanics, not confirmed via a device trace.

## Instrumentation
Not yet added.

## Next step
This needs a design decision, not just a fix — see the two options presented
to the user:
1. Track the name's own last-known position, and only auto-translate it if
   it hasn't moved from that saved position (i.e., only when genuinely left
   behind) — real fix, adds a small piece of persisted state.
2. Remove the collapsed-move auto-reconciliation entirely — no bug, but a
   plain icon-only drag would then leave the name behind with no automatic
   catch-up (matches the "let the user handle it" pattern already used for
   the dropped underline / dropped Recollapse-deferred reconciliation this
   session).
