# B-015: Permission gate silently lets operations proceed unpermitted

**Status:** Fixed

## Symptom

During CR-002 (permission declarations) implementation validation: after
declining permissions via the tap-triggered gate, pressing the Collapse
button showed the "working" overlay and then nothing — no permission
dialog, and the collapse silently didn't happen. Logcat shows
`insertElements failed res={"error":{"message":"File write permission
has not been requested, so related APIs cannot be called.","code":1501}}`
— i.e. `collapseAction`'s `ensureAllPermissions()` gate returned `true`
(proceed) even though WRITE was not actually granted.

## Hypothesis

`ensurePermissions()` (`src/utils/permissions.ts`) calls
`PluginManager.hasPermission(name)` and treats any truthy result as
"already granted," skipping `requestPermission` (and its dialog)
entirely. `hasPermission`'s return shape is undocumented (only
`requestPermission`'s 0/1/2 are confirmed, per SDK_DOC.md) — if it
actually resolves to a `{success, result}`-shaped object (the pattern
every other SDK call in this codebase uses), rather than a raw number,
`if (hasRes)` is **always** truthy (any non-null object is truthy in
JS) regardless of the real permission state. That would make every
`ensurePermissions()` call silently believe it already has every
permission, on the very first check, forever.

## Evidence

Logcat (this session): `revokePermission: op=1/op=2/op=4` fires right
as the button press is routed to the plugin, immediately followed by
`onButtonPress fired` → `collapseAction` → `insertElements failed`
(code 1501) — with **no** `PluginPermMgr: hasPermission`/
`requestPermission` log lines in between, unlike an earlier manual grant
flow in the same session where those log lines clearly appeared.

## Instrumentation

None added yet — evidence so far comes from host-side logcat lines
already present (`PluginPermMgr`, `PluginSecurityMgr`), not from our own
code (which logs via `dlog`, gated by `DEBUG=false` and therefore
invisible in this trace).

## Fix (confirmed)

`ensurePermissions()` (`src/utils/permissions.ts`) no longer calls
`hasPermission` at all — it calls `requestPermission` unconditionally
for anything not yet in the in-memory `GRANTED` cache, trusting only its
documented 0/1/2 result.

## Confirmation

On-device validation (Part A of CR-002's Implementation step 5): denial
triggers the dialog(s) correctly, shows the plugin's own message, leaves
the page unchanged, and a later operation re-asks correctly (nothing
sticks as a false "already granted"). The one remaining failure in that
same validation pass (Part B — Expand not working after Collapse) was
traced to a **separate, unrelated root cause**: B-016 (`userData` not
round-tripping through any SDK read API at all, an external SDK bug).
That confirms B-015's own fix works correctly in isolation.
