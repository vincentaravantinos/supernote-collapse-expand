# B-004: Half-baked Recollapse (frame/strokes left behind) after a complex Expand

**Status**: Fixed — confirmed by the user (no recurrence through extensive
subsequent use since `r101-preservednums-fix-v2`, 2026-07-17). `expandOne`'s fast path now
computes `preservedNums` properly filtered to untagged-only, matching the
fallback path, instead of an unfiltered raw number list. The original exact
failing sequence was never independently re-confirmed (it wasn't a
deliberate, repeatable repro to begin with — it emerged from free-form use).
So far:
- The root cause is a confirmed code defect (traced from a real device log,
  not a guess), and the fix directly addresses it at its source, not a
  narrow patch for one symptom.
- The separate "name jumps on Expand" half of the original combined report
  was independently isolated into three controlled cases (icon moved alone,
  name moved alone, neither moved) — all three now behave correctly.
- The half-baked-Recollapse symptom itself has **not** been re-triggered or
  re-confirmed-fixed — the user is continuing normal use and will report if
  it recurs. Do not treat this as closed until that happens (or enough
  normal use passes without recurrence that it's reasonable to consider it
  resolved) — the user, not elapsed time or a single clean test, decides
  when this is done.
`DEBUG=true` and the filtered background logcat capture stay on for this
continued observation.

## Root Cause (final — supersedes the first, narrower diagnosis below)
`expandOne`'s fast path (`src/logic/expandAction.ts`) computed
`preservedNums` from `PluginFileAPI.getElementNumList()` — every page
number, tagged and untagged mixed together — instead of filtering to
untagged-only the way the fallback path already did. The removed code
comment justified this as an optimization: "the untagged filter is
unnecessary because recollapse's own untagged-check excludes our elements,
so the raw num list is equivalent."

That assumption held for exactly one of the two places `preservedNums` is
consumed — `recollapseOne`'s "absorb new strokes drawn on the section"
logic, which applies its own tag check before ever consulting
`preservedNums`. It did **not** hold for `fastSectionElements`
(`src/logic/recollapseAction.ts`), which excludes any page number appearing
in the persisted `preservedNums` with **no** supplementary tag check:
`candidateNums = allNums.filter(n => !preserved.has(n) && n !== entry.iconNum)`.
If the raw, unfiltered `preservedNums` happened to include numbers
belonging to *this section's own* tagged elements (mask rings, frame,
parts, name strokes), the fast-path Recollapse wrongly treated them as
pre-existing and excluded them from `candidateNums` — never fetched, never
classified, never deleted.

A first, narrower fix attempt (stripping just the name-relocation's old
numbers out of `preservedNums`) addressed one specific *cause* of this
staleness but not the underlying defect — a second occurrence, with no name
relocation involved at all, showed the same class of failure (1 of 10 parts
and the entire mask/frame set excluded). The final fix removes the raw/
unfiltered shortcut entirely: the fast path now always computes
`preservedNums` via a real, filtered element read, exactly like the
fallback path.

## Chain of effects (this occurrence)
1. Section named twice in quick succession (two separate Rename operations).
2. Expand: `preservedNums` captured at the top = 16 values (icon + the
   name's 15 strokes, since nothing else had been inserted yet).
3. Same Expand's reconciliation block detects the icon moved since last
   save, relocates the name: deletes the 15 old-position strokes, inserts
   15 new-position ones (new `numInPage`s). Also inserts ~12 content parts +
   mask/frame.
4. `expandedState.preservedNums` is written as the original (now stale)
   16-value list — none of which match any currently-live element except
   possibly the icon.
5. User presses Recollapse. The section is still in `expandedRegistry`
   (just expanded), so the fast path runs. Evidence is inconclusive on the
   exact candidate-set outcome (that window's own log lines were entirely
   absent — most likely lost to logcat volume from the surrounding verbose
   native logging, not proof either way) — but this is the mechanism most
   consistent with what was observed: frame and some strokes left behind, no
   error reported.
6. A second Recollapse attempt found no `expandedRegistry` entry (the first
   attempt's `recollapseOne` had already run far enough to call
   `forgetSection`, or the entry had otherwise cleared) — went through the
   full fallback path instead, which is immune to this bug, and completed
   cleanly (`getElements(full)=..total=34 el`, `serializeParts parts=12`,
   `deleteElements n=18`).

## Fix (implemented)
`expandOne`'s fast path now computes `preservedNums` by reading elements and
filtering to untagged-only (`readUserData(el) == null`), matching the
fallback path exactly, instead of a raw `getElementNumList()`. Costs one
extra `getElements` call, but only when `capturePreserved` is true (a real
Expand button press, not the live-redraw path). The earlier narrow patch
(stripping name-relocation's old numbers) was removed as redundant — with
`preservedNums` never populated with tagged numbers to begin with, there's
nothing left to strip.

## Validation
- Isolated controlled cases (icon moved alone, name moved alone, neither
  moved) all confirmed correct on-device against the final fix.
- The exact original half-baked-Recollapse sequence was not independently
  re-confirmed — it was never a deliberate, repeatable repro. Passive
  observation (`DEBUG=true`, background logcat capture) stays on as a
  safety net.
