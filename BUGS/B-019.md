# B-019: Dragging native/untracked content (esp. links) into an expanded section misbehaves

**Status**: Parked — one confirmed strand fixed (see below), the other not reproducible

## Strand A — Recollapse orphaning a dragged-in link (FIXED, confirmed on-device)

**Symptom:** drag a native link (annotation + member strokes) into an
expanded section's zone, then Recollapse: the member strokes are
absorbed correctly, but the link annotation is left behind on the page,
empty, referencing stroke numbers that no longer exist. Re-expanding
shows the strokes but not the link, now hidden under the freshly
redrawn zone.

**Root cause:** `recollapseAction.ts`'s absorb-scan (`ABSORBABLE_TYPES`)
excluded `ELEMENT_TYPES.LINK` — only strokes/text/geometry were
absorbed, so a dragged-in link's member strokes got absorbed
individually while the link element itself was skipped and orphaned.

**Fix:** added `ELEMENT_TYPES.LINK` to `ABSORBABLE_TYPES`. No other
change needed — `resolveLinkMemberIndices` (already called on the full
absorbed list) already stitches a link back together with its member
strokes once both are in the same batch, and already handles the
partial-drag case (drops the link with an alert, keeps the strokes) via
existing, previously-unexercised logic. Confirmed working on-device
after repeated testing.

## Strand B — Page "-1" + app-wide corruption after icon-drag redraw (Parked, not reproducible)

**Original repro (link ends up overlapping the zone):**
1. Create strokes, Collapse them.
2. Move the icon (collapsed).
3. Expand.
4. Move the icon (live-redraw, to make more room).
5. Add strokes outside the section's frame.
6. Turn those strokes into a native stroke link (still outside the frame).
7. Drag the link (native move) into the section's area.
8. Move the icon again (another live-redraw).

Step 8 landed on page **-1**. Swiping away and back landed on page 1,
where the section (with its original step-1 strokes) was present but
the link from steps 6-7 was gone.

**Later variant (link stays outside, never overlaps):** collapse
strokes+link, create a second link outside the section, expand (outside
link stays outside), move the icon to resize — also landed on page -1
once, with the app additionally left needing a manual refresh after
every subsequent action/page change (a known trail-cache desync
symptom this project has seen before, normally cleared only by
restarting the Note app — done, and it worked).

**Investigation:** added a shared link/numbering probe (logging every
link's `controlTrailNums` + page-wide `numInPage` list at checkpoints
around Collapse/Expand/redraw's delete+insert calls) to test the
hypothesis that deleting/reinserting elsewhere on the page shifts a
link's referenced numbers out from under it. Could not reproduce either
variant with the probe in place. Removed the probe (to rule out its own
added latency as a confound) and retested extensively, varying order
and combinations — still not reproducible.

**Working theory:** the page-(-1) crash and subsequent corruption were
most likely a downstream symptom of the same trail-cache desync this
project already knows about, accumulated over a long, intense
stress-testing session rather than a deterministic bug reachable from a
clean state. Not ruled out that the probe's added latency was
incidentally masking a real race (a lighter possibility, not
contradicted by the clean-build retest since removing latency should
make a race easier, not harder, to hit — its absence here is weak
evidence either way).

**Next step:** if this recurs, re-add the link/numbering probe (see git
history for `src/utils/b019Probe.ts`, removed 2026-09-24) and capture a
fresh trace. Also worth capturing a build with `DEBUG=true`
(`constants.ts`) next time, since a separate, still-unexplained hang
was observed once in `rebuildStrokeLinks`'s reload-retry path during
this same testing round (no trace beyond one `console.error` line, due
to `DEBUG=false` in production builds) — unclear if related.
