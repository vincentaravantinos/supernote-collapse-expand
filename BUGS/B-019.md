# B-019: Icon-drag redraw after manually dragging outside content into an expanded section landed on "page -1"

**Status**: Pending — not yet investigated, reported during B-018 stress-testing

## Symptom

Reported sequence:
1. Create strokes, Collapse them.
2. Move the icon (collapsed).
3. Expand.
4. Move the icon (live-redraw, to make more room).
5. Add strokes outside the section's frame.
6. Turn those strokes into a native stroke link (still outside the frame).
7. Drag the link (native move, not a plugin action) into the section's area.
8. Move the icon again (another live-redraw).

Step 8 landed on page **-1** (page numbers are normally 1-indexed;
should be impossible). Swiping away and back landed on page 1, where
the section (with its original step-1 strokes) was present but the
link from steps 6-7 was gone.

## Hypothesis (unconfirmed)

The link was drawn and dragged in via native gestures, never through
this plugin's own Collapse/absorb mechanism — so it was never tagged
`CE_PART:<id>` for this section. The icon-drag redraw
(`iconMoveRedraw.ts`) only re-serializes/deletes/reinserts elements
already tagged for the section; it has no absorb-untracked-content step
(unlike Recollapse, per SPEC.md's "Modifying the content of an existing
section"). Deleting the old mask/frame by `numInPage` could shift
other elements' numbers; if the untracked link's number shifted into a
stale reference used elsewhere, that could explain both its
disappearance and a garbage computed value like a page number.

Not confirmed — no instrumentation added yet, and dragging arbitrary
outside content into an already-expanded section isn't a documented/
supported flow to begin with (closest existing non-goal: SPEC.md
"Sections do not nest or overlap").

## Next step

Not investigated further yet. If reproducible outside of deliberate
stress-testing, revisit with instrumentation on the icon-drag path
specifically around the delete/reinsert numbering.
