# B-025: Two icons (one +, one -) appeared after a pencil drag on the resize handle

**Status**: Parked (part A fixed and confirmed; part B open)

## Symptom

1. Section expanded (icon shows ⊖).
2. User put the pen down on the resize handle (palm possibly resting
   on the screen, nowhere near any icon/handle).
3. User lifted the pen **without moving it**.
4. The plugin's "Working..." overlay appeared, with a native "loading"
   popup behind it (consistent with our `reloadFile()`).
5. After one or more refreshes, a second icon appeared next to the
   first, in the ⊕ (collapsed) state.

Both icons then behave as fully independent sections with the same
content: each expands on its own and can be moved independently
(consistent with CR-010's self-heal having given the ⊕ copy a new id).

## Hypothesis (unconfirmed, two parts)

**A. Why a redraw ran at all.** A handle-triggered redraw has no
"did it actually move" check (the icon trigger has one). The only
guard is `isTapDistance` in `onMotionUp`. If the palm's UP event
arrives with the palm's own coordinates while the pen's DOWN set the
candidate on the handle, the distance check fails and the redraw
runs. The finger/pencil consistency check doesn't catch it: a palm
reported as multi-pointer isn't a "qualifying finger", so it matches
the pen's "not a finger" at DOWN and is treated as a pencil drag.

**B. Where the ⊕ copy came from.** `⊕` is written onto an icon in
only two places: at Collapse, and in `expandOne` when its insert
fails (`textContentFull = insertOk ? ⊖ : ⊕`). The redraw's failure
fallback then also writes `isExpanded:false`. So the redraw most
likely hit `expandOne`'s insert-failed branch. The ⊖ original surviving
with its content means the redraw's delete didn't land either (it is
only logged, not verified). A write to the icon then produced a
second element instead of modifying the existing one. Candidates:
the icon's `textRect` now rewritten on every handle redraw (CR-009,
original hypothesis), and/or `writeSection`'s retry loop re-sending
`modifyElements` after a failed read-back.

## Evidence

- User's detailed report above.
- 2026-09-29 logcat (device still connected): the plugin logs errors
  only, and no redraw-path error lines appear. Not conclusive.

## Instrumentation

Not yet added. Proposed: log the icon's `numInPage` (and a short id) at
three checkpoints in a handle-triggered `redrawSectionBox` call — right
after classification, right after the stash `writeSection` call, and
right after `expandOne`'s own `writeSection` call — to see whether a
second, distinct `numInPage` for a `CE_PLUG` shows up at any point, and
whether it correlates with the unconditional write-back specifically
(e.g., temporarily gating it back to the old `iconWasOverlapping`
condition for a handle trigger and seeing if the symptom stops).

## Next step

Part A fixed: a handle-triggered redraw now returns early unless the
handle moved > 1px from where the last-drawn zone put it
(`redrawSectionBox`). Confirmed on-device: select-and-lift with palm
resting no longer redraws; pencil/finger handle and icon drags still
resize normally.

Part B still open, not reproducible on demand: how a failed redraw can
leave a ⊕ duplicate icon next to a surviving ⊖ section. If it recurs
(via any real drag), add the instrumentation above, focused on
`writeSection`'s modify/verify/retry loop and the redraw's unverified
`deleteElements`, and capture logcat right away.
