# B-005: Renaming with old + new ink in the same lasso drops the old ink

**Status**: Fixed — `index.ts`'s classification now collects re-selected
`CE_NAME` strokes (`nameTaggedInLasso`) instead of silently dropping them;
`handleNameAction` merges the ones matching the target section with the
fresh untagged ink before rebuilding the name. Confirmed on-device: writing
"2" in among an existing "Name" and re-lassoing both now produces "Name 2".

## Symptom
Section is named "Name". User writes "2" in among the existing strokes
(intending the name to become "Name 2"), lassoes the icon together with the
whole resulting selection ("Name" + "2"), and presses the plugin button. The
new name becomes just "2" — the old "Name" ink is silently dropped, not
merged in.

## Hypothesis (confirmed via code trace, not yet verified on-device)
`handleNameAction` only treats **untagged** strokes as the new name's
content (`strokeCandidates = nameCandidates.filter(...)`, and
`nameCandidates` itself is built in `index.ts`'s classification loop from
only the `!ud` — untagged — branch). The old "Name" strokes are already
tagged `CE_NAME:<sectionId>` from the prior naming, so they're excluded from
`nameCandidates` regardless of being in the lasso. Separately, a rename
always deletes **every** existing `CE_NAME` element for the section
(`existingNameEls`, found via a fresh scan, not limited to what's in this
lasso) as part of "Replace" semantics. Net effect: old tagged ink in the
lasso is deleted like normal replace behavior, but never contributes to the
new name's content — only fresh untagged ink does.

## Fix Proposal (not yet implemented — pending confirmation)
Let a rename's new content include CE_NAME strokes belonging to *this same
section* that are re-selected in the current lasso, not just untagged ink:
1. `index.ts`'s classification loop: also collect `ud.kind === 'name'`
   elements into a separate list (e.g. `nameTaggedInLasso`) — today they
   silently fall through unclassified.
2. Pass that list into `handleNameAction` alongside `nameCandidates`.
3. Inside `handleNameAction`, filter it to strokes whose tag id matches
   `target.section.id` (ignore stray name strokes from a different section
   that happened to be swept into the same lasso) and merge them with
   `strokeCandidates` before serializing — both become the new name's
   content.
4. `existingNameEls` (all of the section's current name strokes, lasso or
   not) are still all deleted, same as today — the ones that were re-selected
   get recreated fresh as part of the new name; any left out of the lasso
   are dropped, matching today's "Replace" semantics for anything not
   explicitly re-selected.
