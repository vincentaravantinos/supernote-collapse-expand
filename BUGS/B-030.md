# B-030: Erased name reappears after tapping the icon

**Status**: Parked

## Symptom

User erased a section's name entirely, then tapped the section's icon: the
leftover underline disappeared (expected, REQ-660) but the erased name
reappeared.

## Hypothesis

The erase only lives in the note's cached copy until it's saved; our
writes go to the real file, and `reloadFile()` re-displays the real file.
If anything in the tap's sequence writes + reloads before the erase is
flushed to the real file, the display reverts to the real file — which
still has the name. Open question: whether this is specific to the
underline cleanup (a delete + reload after the operation) or happens for
any erase followed by a tap (pre-existing and more serious).

## Evidence

logcat 13:56:49: `stale-cache retry recovered a hit` (the tap), several
`reloadFile() timed out`, then 13:57:06 an Expand.

## Instrumentation

Temporary `[B-030-PROBE]` counts of name/underline elements per section at
tap start (A0), after saveCurrentNote (A1), before the underline cleanup
(B) and after it (C). Removed after 4 clean runs.

## Next step

Parked. Both failing runs happened while nearly every `reloadFile()` call
was timing out (a degraded note-app state in which its cached page and the
real file drift apart); after a plugin reinstall/restart with no timeouts,
4 runs of erase-whole-name + tap were all clean (names=0 at every
checkpoint, underline removed, nothing restored). Working theory: a symptom
of that degraded host state, not plugin logic. If it recurs, re-add the
probe and capture logcat while the timeouts are occurring.
