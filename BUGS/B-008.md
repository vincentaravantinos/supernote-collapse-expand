# B-008: Native toolbar submenu tap over a section icon triggers the plugin's tap-toggle

**Status**: Fixed — confirmed by the user on-device (2026-07-14). Final fix
added a Cancel button to the working card (appears after 7s) instead of a
watchdog — see DECISIONS.md 2026-07-14 "User-triggered Cancel instead of a
blind watchdog for a stuck 'working' card". The underlying race (a tap
simultaneously switching the foreground app mid-operation) can't be
prevented — no SDK signal exists for it — but is now recoverable
immediately without a device restart.

## Symptom
A native Supernote toolbar submenu (unrelated to the plugin) was open and
happened to sit over a collapsed/expanded section's icon on the page. Tapping
an option in that submenu landed at coordinates that also matched the icon's
hit-box. The plugin's single-finger tap-toggle fired (treating it as a tap on
the icon) while the native app was simultaneously handling the submenu tap —
the two colliding broke the interaction entirely.

## Hypothesis
Per `SDK_DOC.md`'s existing notes on `registerMotionListener`: it "fires for
*every* touch," carries "no element identity — only coordinates," and
critically **no event fires when a selection is made or a menu opens**. There
appears to be no SDK-level signal a plugin can check for "is native UI
currently open/consuming this touch" — the motion listener just reports raw
x/y in canvas space regardless of what's drawn on top. If that's accurate,
this isn't a bug in our tap-toggle logic specifically — it's a structural gap
in what the SDK exposes, and our tap-toggle (`iconTapToggle.ts`) has no way
to distinguish "the user tapped the canvas at the icon's position" from "the
user tapped native chrome that happens to overlap those coordinates."

I don't see an obvious mitigation from the plugin side given that gap — happy
to be wrong, but wanted to flag the uncertainty rather than propose a fix
that can't actually work.
