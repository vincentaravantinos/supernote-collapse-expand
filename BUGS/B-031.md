# B-031: One note constantly fails mid Collapse/Expand with an error

**Status**: Fixed

## Symptom

On one specific note, Collapse and Expand constantly fail partway through
with an error. Other notes are not reported as affected.

## Hypothesis

**Current:** a single Collapse on 2026-10-19 created three icons (stale-read
retry in collapse's insert-verify loop). The self-heal then gave them
separate ids, leaving three identical, stacked sections. See Evidence.

**Superseded (first trace):** The Collapse that "does nothing" (spinner, no change) never reaches its
delete step. On 1.3.0 (11:44:07) it ran saveCurrentNote → getElements →
modifyElements → getElements → setLassoBoxState, with no deleteElements and
no error logged. It also never made the per-element verify reads that
writeSection does after a modify, so this is probably not the normal
recollapse path. Which code path actually ran is still unknown, because
DEBUG logs are off. Every reloadFile() on this note times out (the note app
logs `reloadCurrentNotePage isLoadCurrentLayersRunning return`), and that
probably explains why the reads are stale and the screen never refreshes.

## Evidence

- Device is running a pre-1.3.0 instrumented build: logcat shows
  `[B-030-PROBE]` lines, a probe that was never committed and is absent from
  the 1.3.0 package. The 1.3.0 `.snplg` was pushed to the device but never
  installed.
- 11:41:05 `reloadFile() timed out after 5000ms` (the degraded state seen in
  B-026/B-027/B-030).
- 11:41:12 Expand: `insertElements reported success but only 0/47 tagged
  elements found (read attempt 0) — re-reading`; by 11:41:20 the page total
  went 87 → 134 (= +47), so the insert did land.

## Instrumentation

Build `1.3.0-b031`: DEBUG on, plus temporary `[B-031]` logs: runExclusive
START/BODY-DONE/END/DROPPED, TAP hit, R0–R5 (recollapse: fast/full, icon
found, classify counts, payload, writeSection result, delete result), W1/W2
(writeSection modify + each verify read), LR0 (live redraw entry),
reloadFile resolve time.

- 1.3.0 installed 11:43:31 (`init build=1.3.0`). Tap-Expand at 11:43:44 went
  through (0/47 on first read, then landed). Collapse at 11:44:07: no
  deleteElements, no plugin error, only the expected setLassoBoxState 904.
  reloadFile timed out on every call.

- b031 trace (11:55–11:58): every operation **succeeded**: writes
  confirmed, deletes ok, no errors. But the page holds **three sections with
  identical content** (41 parts each, payload ~79.8 KB) and three
  different ids: `mvezob0i-twbtm6` (icon 226), `mvezohfu-ur48jj` (227) and
  `mvezojcg-x7km2o` (228), all stacked in the same spot. Every user-visible
  oddity follows from that: recollapsing one leaves an identical copy
  visible ("no collapse"), the next tap collapses the second copy
  ("collapsed entirely"), and expanding another copy then draws on top of
  it ("duplicate section").
- Decoding the ids as Date.now(): created 2026-10-19 10:25:09.570, +8.3 s and
  +2.5 s later.
- `collapseAction`'s insert-verify loop re-inserts the icon after a single
  read that missed it. The id is generated once, before the loop, so a stale
  read (reloadFile no-op/timeout, the B-027 pattern) produces 2–3 icons
  with the **same** id. The post-op `buildIconCache({repair})` self-heal
  (REQ-400) then gives each collapsed duplicate a new id, one writeSection
  at a time, which would explain the +8.3 s / +2.5 s gaps. B-027's fix
  (re-read before re-sending) went into expandOne and writeSection but not
  into collapse.

- Fix build (12:10–12:14): only one Collapse ran (button), and its first
  read already saw the icon, so the fixed retry path wasn't exercised. The
  stale read did occur in Expand (12:14:22, 0/53 right after a reloadFile
  that **resolved** in 318 ms), so a reload that reports success doesn't
  guarantee fresh reads (note app: `isLoadCurrentLayersRunning return`).
- Many "reloadFile() timed out" lines are spurious: `reloadFileWithTimeout`
  never clears its timer, so the message prints 5 s later even when the
  reload had resolved. That misled the first diagnosis.

## Resolution

Collapse now re-reads (up to 3×) instead of re-inserting after a reported
success, and deletes any extra icon copies before deleting the originals.
reloadFileWithTimeout now clears its timer (no spurious timeout logs).
Verified on-device by fault injection: a simulated stale first read
re-read and found the single icon; a forced double insert detected 2
copies and removed 1. The affected note's existing stacked copies need
manual cleanup.
