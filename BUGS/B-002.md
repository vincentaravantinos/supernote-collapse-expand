# B-002: Renaming a section makes the erased old name reappear

**Status**: Fixed — `handleNameAction` now calls `PluginNoteAPI.saveCurrentNote()`
as its first step, matching every other action handler. Confirmed on-device:
erasing an old name and renaming no longer resurrects it.

## Symptom
1. User erases a section's existing name strokes (native eraser).
2. Writes new name strokes elsewhere on the page.
3. Lassoes the new strokes together with the section's icon.
4. Presses the plugin button (Name/Rename).
5. The operation completes, but the old (erased) name strokes reappear.

## Hypothesis
`handleNameAction` (`src/logic/nameAction.ts`) never calls
`PluginNoteAPI.saveCurrentNote()` before reading `getElements` or mutating —
every other action handler in this codebase (`collapseAction.ts`,
`expandAction.ts`'s `expandSections`, `recollapseAction.ts`'s
`recollapseSections`) explicitly flushes with `saveCurrentNote()` as its
first step, specifically to avoid the documented SDK behavior in
SDK_DOC.md ("`reloadFile` discards unsaved strokes"): edits made
interactively (drawing, and presumably erasing) live only in a **cached**
copy until saved; `reloadFile()` reloads cache←real, so anything not yet
saved to the real file is discarded/reverted when `reloadFile()` runs.

`handleNameAction` calls `PluginCommAPI.reloadFile()` at the end (to surface
its own inserts/deletes) without ever having flushed the user's prior erase
to the real file first. If the erase is still cache-only at that point, the
real file on disk still has the old name strokes — `reloadFile()` would
reload the cache from that stale real file, making the erased strokes
reappear. This is a plausible mechanism (matches documented SDK behavior and
a pattern consistently applied everywhere else in this codebase except this
one file), not yet confirmed via a trace.

## Evidence
None yet — hypothesis is from code/doc inspection only.
