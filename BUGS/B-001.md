# B-001: Named section's ink vanishes after confirming Name/Rename

**Status**: Fixed — `nameAction.ts`/`expandAction.ts`/`iconMoveRedraw.ts` now
compute the EMR translation delta by converting two absolute points and
subtracting, instead of converting the raw pixel delta directly. Confirmed
on-device: the name now lands next to the icon instead of off-page. Root
cause promoted to SDK_DOC.md ("Compute `emrDelta` from two converted points,
never by converting a bare delta").

## Symptom
User selects a few handwritten strokes next to a collapsed section's icon
plus the icon itself, presses the plugin button. The confirm dialog appears
("Set this section's name..."). After confirming: the original selected
strokes disappear, no name strokes appear anywhere near the icon — only the
icon itself remains. No error alert is shown.

## Hypothesis
`rebuildNameElements` (src/logic/nameAction.ts) computes the EMR-space
translation delta by converting the raw **android-pixel delta** `(dxPx, dyPx)`
directly through `PointUtils.androidPoint2Emr`, i.e. treating a delta vector
as if it were an absolute point:

```ts
const emrDelta = PointUtils.androidPoint2Emr({ x: dxPx, y: dyPx }, pageSize);
```

Every other place in this codebase that needs an EMR-space delta
(`expandAction.ts`'s `emrNow`/`emrSaved`/`emrDelta`) instead converts **two
real absolute android points** to EMR space independently and *then*
subtracts:

```ts
const emrNow = PointUtils.androidPoint2Emr({ x: iconRectNow.left, y: iconRectNow.top }, pageSize);
const emrSaved = PointUtils.androidPoint2Emr({ x: section.iconRect.left, y: section.iconRect.top }, pageSize);
const emrDelta = { x: emrNow.x - emrSaved.x, y: emrNow.y - emrSaved.y };
```

That pattern only differs from "convert the delta directly" if
`androidPoint2Emr` is a pure linear scale through the origin — if it has any
additive/offset term (e.g. a Y-axis flip or page-origin offset, plausible
given android and EMR coordinate systems don't necessarily share an origin
or axis direction), converting a bare delta injects a spurious constant
offset into every rebuilt stroke's position. That would place the "new" name
strokes at a wrong — likely off-page or otherwise invisible — location, while
`insertElements` still reports success (no alert fires) and the original
candidate strokes are still deleted afterward (deletion only happens after a
successful insert) — matching exactly what was observed.

Same bug is very likely also latent in the two other new call sites
(`expandAction.ts`'s collapsed-icon-move reconciliation, and
`iconMoveRedraw.ts`'s live-drag reconciliation), which compute their own
`emrDelta` the same wrong way before calling `rebuildNameElements` — those
paths haven't been exercised yet on-device.
