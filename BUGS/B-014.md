# B-014: Stroke link's visual link indicator doesn't survive Collapse/Expand (functionality does)

**Status**: Parked — could not reproduce.

## Symptom (as originally reported)
Collapse a selection containing a handwritten ("stroke") link:
- **While collapsed**: the icon area showed a leftover visual cue of a link
  (a frame/link-icon artifact) even though the strokes themselves were
  correctly hidden.
- **After Expand**: the strokes reappeared with no link visual at all —
  looked like plain, unlinked handwriting. Tapping them still navigated to
  the link's target (functionality intact), but nothing about their
  appearance indicated they were a link.

Observed once during the release corner-case sweep (build r123).

## Investigation
Added always-visible (`console.error`, ignores `DEBUG`) instrumentation
that does a fresh element read and dumps every link element's
`category`/`controlTrailNums`/`rect`/`userData` plus every tagged stroke,
at before/after checkpoints around collapse, expand (including a per-link
checkpoint inside `rebuildStrokeLinks`), and recollapse (build
r129-b14-link-probe). With that instrumentation in place, re-ran the exact
sequence — collapse a section containing a link, expand, recollapse — first
with a simple case, then a more complex one. Both times, everything behaved
correctly: no leftover collapsed-state artifact, link visual present after
expand. Could not reproduce across multiple attempts.

Code-level review of the relevant paths (`collapseAction.ts`,
`strokeLinkExpand.ts`, `elementSerializer.ts`'s link handling) turned up no
special-casing gap that would obviously cause this — a stroke-link element
is a generically-tagged (`CE_PART:<sectionId>`) element like any other and
should be captured and deleted/restored the same way regular content is,
which is consistent with not being able to reproduce it.

## Hypothesis (unconfirmed)
Possibly a one-off rendering-cache artifact from whatever state the note
was in during the original corner-case sweep, not a deterministic bug in
this plugin's logic — but this is speculation; it was never caught in the
act.

## If this resurfaces
The instrumentation approach (a shared `dumpLinkState(label, filePath,
page)` helper doing a fresh `getElements` read, called at
before/after checkpoints around collapse/expand/recollapse, plus a
per-link checkpoint inside `rebuildStrokeLinks`'s loop) is a fast, proven
way to get a clear trace — was removed after parking (per bug-investigation
step 9) rather than left logging permanently, but the design is documented
here so it can be dropped back in quickly rather than redesigned from
scratch.
