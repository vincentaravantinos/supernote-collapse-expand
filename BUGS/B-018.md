# B-018: Recollapse/Expand of a section with a stroke link can partially complete

**Status**: Fixed — confirmed on-device across 5 clean collapse → expand →
recollapse cycles, including recollapsing immediately after expand (the
condition that failed most often before).

## Symptom

Recollapsing or expanding a section that contains a stroke link plus
other content can partially complete instead of fully succeeding, or
appear to do nothing at all with no visible error.

## Root causes (three distinct issues, all confirmed)

1. **`deleteElements` can silently apply to only some of its targets**
   while still reporting `success: true` (recollapse) — same bug class
   CR-004 found in `batchUpdatePageElements`.
2. **A `reloadFile()` that resolves under its own timeout doesn't
   guarantee `getElements()` immediately reflects it** (expand) — the
   member-num recovery read can come back short even without a hang.
3. **`alert()` silently no-ops while the busy view (`showPluginView`) is
   showing** — already documented in this codebase's own SDK_DOC.md,
   but not consistently applied. Every action (collapse/expand/
   recollapse, plus shared helpers `ensurePermissions` and
   `resolveLinkMemberIndices`) is only ever invoked *after* its caller
   already shows the busy view, so **every failure-path alert in this
   whole codebase has been invisible** — explaining why failures looked
   like silent no-ops instead of showing the intended error message.
   `nameAction.ts` was already correct (its caller explicitly closes the
   view around it) — everything else wasn't.

## Fixes

- `recollapseOne`: re-read after `deleteElements` and retry whatever's
  still actually there (up to 3 attempts).
- `rebuildStrokeLinks`: retry the reload+read (up to 3 attempts) if
  `memberNums` comes back short of what was just inserted.
- New `alertOverBusyView()` helper (`src/utils/busyView.ts`): closes the
  busy view first, then alerts. Applied to every failure-path `alert()`
  that runs after a busy view may be showing — `collapseAction.ts`,
  `expandAction.ts`, `recollapseAction.ts`, `permissions.ts`'s denial
  alert, and `elementSerializer.ts`'s dropped-link alert (which is why
  `resolveLinkMemberIndices` is now `async`). `nameAction.ts` was left
  as plain `alert()` — confirmed its caller already closes the busy view
  around the whole call, so it was never affected.

None of this changes write ordering or crash-safety — only verification/
retry around existing calls, and *where* an already-intended alert is
shown.

## Round 2 (after the above still silently failed)

Confirmed via a clean live repro: `recollapseOne` ran to completion with
**zero** errors or alerts logged anywhere, yet the icon glyph never
flipped and nothing was deleted. That's not a caught failure at all —
it means `recollapseOne` found literally nothing tagged for this
section (`partEls`/`maskEls` both empty), which an expanded section
should never have. Fix: if both come back empty from whatever element
list the caller supplied (often the "fast path"'s narrower scan),
re-fetch the full page fresh and re-classify before accepting "nothing
to do".

Separately, `PluginManager.showPluginView()`/`closePluginView()` both
resolve to a plain `boolean` (confirmed against `NativePluginManager`'s
own type declaration), not `{success, result}` like every other SDK
call. `closeBusyView`'s `res?.success` check was therefore always
`undefined` → always logged as a false failure, regardless of the
actual result — a pre-existing bug (present before this session's
refactor too), fixed now. This was cosmetic (the logging lied, not the
actual close), but worth ruling out as a real problem.

## Round 3 — the actual root cause

Confirmed via a clean repro with clear before/after evidence: the
"recollapse" tap's own log showed `"expand setLassoBoxState"` — meaning
the *second* tap actually re-ran **Expand**, not Recollapse. `hit.section
.isExpanded` (read from the icon's persisted userData) was still `false`
even though the first Expand had visibly succeeded moments earlier.

Root cause: `writeSection`'s `modifyElements` call (used to flip the
icon's `isExpanded` flag and glyph) can report success without the
write actually landing — the same bug class as `deleteElements` and
`batchUpdatePageElements`, now confirmed for `modifyElements` too. Since
a subsequent tap classifies purely on this flag, a silently-reverted
`isExpanded: true` sends the very next tap back into `expandSections`
on an already-expanded section — which, since `collapsedElements` is
only cleared in that *same* failed write, still holds the original
content, so it attempts to insert a **second** copy of everything,
stacked exactly on top of the first (may be invisible if the position
matches exactly).

Fix: `writeSection` now reads the icon back after `modifyElements` and
confirms `isExpanded` actually matches what was just written, retrying
the write (up to 3 attempts) if not — same verify-and-retry shape as
the delete and reload fixes above, applied to the one remaining
unverified write in this whole flow.

**Risk to check for**: if this happened before the fix shipped, a
previously "successful" Expand may have silently duplicated content
underneath what's visible. Worth a visual double-check (nudge the
visible content slightly, or Recollapse and see if two copies come
back) on any section that went through this failure mode.

## Next step

On-device: repeat the tap-triggered Recollapse/Expand of a fresh
section containing a stroke link. Two possible outcomes are both
progress: it now fully completes every time (bugs 1+2 fixed), or it
still fails sometimes but **now shows a specific alert explaining why**
