# B-018: Recollapse/Expand of a section with a stroke link could partially complete

**Status**: Fixed — confirmed on-device across multiple collapse → expand →
drag-resize cycles with a stroke link present, including immediately after
a previous action (no manual refresh or app restart needed).

## Symptom

Recollapsing or expanding a section that contains a stroke link plus
other content could partially complete instead of fully succeeding —
some content deleted/inserted, some not — or silently do nothing at
all with no error shown. The icon-drag live-redraw path (resizing an
expanded section by dragging its icon) was the hardest-hit and last to
be fixed.

## Root causes (five distinct issues, all confirmed on-device)

1. **`deleteElements`/`modifyElements` can report success without the
   change landing** — not limited to batches, confirmed for ordinary
   single-target writes too (`recollapseOne`'s delete,
   `writeSection`'s icon update).
2. **A `reloadFile()`-then-read can be stale even when the reload
   resolves under its own timeout** (`rebuildStrokeLinks`'s member-num
   recovery).
3. **`writeSection`'s own verification was checking the wrong thing** —
   comparing only the `isExpanded` flag, which doesn't change value on
   a same-state write (e.g. the icon-drag redraw's content-only stash).
   A failed stash could look "confirmed" and the caller would then
   delete the only real copy of the content. Fixed by comparing the
   full raw `userData` string instead of one parsed field.
4. **`expandOne` didn't revert cleanly on failure** — it always marked
   the icon "expanded" regardless of whether the insert actually
   succeeded, leaving an inconsistent state (expanded flag + intact old
   backup) that no normal tap could recover from. Fixed to fully revert
   to the pre-attempt state on failure. The icon-drag redraw path
   additionally needed its own explicit fallback to "collapsed" when
   its own re-insert failed, since by that point the old on-page
   content was already gone and `expandOne`'s generic revert alone
   wasn't a safe end state for that specific caller.
5. **`insertElements` could silently insert nothing at all — not a
   read-timing issue, not a tag mismatch — specifically right after
   this same function's own `deleteElements` call, in the icon-drag
   redraw sequence.** A `saveCurrentNote()` flush between the delete
   and the following insert resolved it. A side effect surfaced after
   that fix: the on-screen render stopped auto-refreshing for this
   path specifically (data was correct, display was stale) — resolved
   by re-adding a timeout-guarded `reloadFile()` at the very end of the
   redraw, which — unlike earlier in the same sequence — no longer
   hangs now that the real timing issue underneath it is fixed.

## Fixes

- `recollapseOne`: re-fetches and aborts cleanly (alert, nothing
  changed) if no tagged content is found for the section, even after a
  fresh full read — previously fell through and could write an empty
  backup. Also retries its delete against whatever's still actually
  there.
- `rebuildStrokeLinks`: retries member-num resolution (plain read
  first, reload as fallback only if needed); aborts the whole rebuild
  — not just that one link — if the count still comes up short after
  retries, rather than building a link with an incomplete member set.
- `writeSection`: verifies by comparing the full `userData` string,
  not one field; retries the write itself if it doesn't match.
- `collapseAction`/`expandAction`: verify their own inserts actually
  landed (icon insert; mask+content insert) before proceeding to
  anything destructive or before clearing the backup.
- `expandOne`: reverts fully to the pre-attempt state on any failure
  (glyph, `isExpanded`, backup, `preservedNums`, `contentShift` all
  revert together) instead of partially committing.
- `iconMoveRedraw.ts`'s `redrawSectionBox`: explicit fallback to a
  clean collapsed state if the post-delete re-insert fails; a
  `saveCurrentNote()` flush between deleting old content and inserting
  the new content at the resized position; a timeout-guarded
  `reloadFile()` at the end to keep the display in sync.
- Shared `reloadFileWithTimeout()` extracted (`src/utils/reloadFile.ts`)
  and used consistently by every verification read added above — an
  earlier round of this fix used a raw `getElements()` without it in
  several places, which could itself produce false "the write failed"
  verdicts.

None of this changes write ordering or crash-safety — only
verification/retry around existing calls, and ensuring a failure
reverts fully instead of partially.
