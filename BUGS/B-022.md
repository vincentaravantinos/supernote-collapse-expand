# B-022: Icon dragged deep inside an expanded section's own content can leave strokes outside the redrawn zone

**Status**: Fixed — confirmed on-device

## Symptom

While a section is expanded, dragging its icon to a position deep
inside the section's own content (not cleanly outside it on any edge)
can result in the redrawn zone/frame no longer fully containing all of
the section's strokes — some strokes end up visibly outside the
frame's boundary after the redraw.

## Root Cause (confirmed via code trace)

`geometryHelpers.ts::stretchZoneToIcon`: when the icon ends up
overlapping the computed zone (exactly the "dragged deep inside the
content" case — none of the four per-side stretches clear it), the
whole zone is translated (`shiftDx`/`shiftDy`) away from the icon so it
doesn't sit on top of it. The function's own doc comment says this
delta is meant for "the caller to move the actual content strokes by
the same amount" — and `recollapseAction.ts`'s caller does exactly
that. `iconMoveRedraw.ts::redrawSectionBox`'s caller does not — it
deliberately destructures only `{ zone }`, discarding `shiftDx`/
`shiftDy`, per its own explicit design choice ("a live redraw's content
must stay exactly where it is"). When the icon overlaps the zone deeply
enough that this shift fires, the zone moves but the content doesn't —
so part of the content can end up outside the zone's new bounds.

## Expected behavior (per user)

If honoring both "icon must clear the zone" and "zone must fully
contain the content" isn't possible (icon dragged literally into the
content's own footprint), containment wins: the zone shrinks/shifts
only as much as still keeps every stroke fully inside it, even if that
means the icon ends up slightly overlapping the zone/mask instead.

## Fix Proposal

Clamp the shift itself inside `stretchZoneToIcon`, not just report it:
cap `shiftDx`/`shiftDy` so the shifted zone edge never crosses the
content bbox's own edge (`r`, already computed in that function) —
i.e. the zone is guaranteed to always contain `r`, and the icon may
end up overlapping the zone as the fallback instead. This fixes both
callers:
- `iconMoveRedraw.ts` (doesn't apply the shift to content at all): the
  zone can no longer end up excluding content, since it's clamped to
  never shrink past the content's own bounds in the first place.
- `recollapseAction.ts` (does apply the shift to content): unaffected
  in ordinary cases; in the same extreme case, it would previously
  shift zone+content together by an unclamped amount — clamping just
  means less shift is applied when the icon is deep inside, same
  "containment wins" trade-off, consistent between both callers.

Concretely: after computing the unclamped `shiftDx` (or `shiftDy`),
clamp it — for the "shift right"/"shift down" (positive) sub-case,
`Math.min(shiftDx, r.left - zone.left)` (`r.top - zone.top` for dy);
for the "shift left"/"shift up" (negative) sub-case, `Math.max(shiftDx,
r.right - zone.right)` (`r.bottom - zone.bottom` for dy) — since
`zone.left <= r.left` and `zone.right >= r.right` always hold before
the shift (symmetric for top/bottom), these bounds are always on the
correct side of zero.

## Next step

Fixed in two parts, both confirmed on-device: (1) the shift is now
clamped so it can never push a zone edge past the content's own
bounds, guaranteeing full containment; (2) since that clamp can leave
the icon overlapping the zone, `iconMoveRedraw.ts` now projects it to
just outside the zone's nearest edge and writes that position back to
the actual page element (see DECISIONS.md 2026-09-25). Added REQ-250
and REQ-260 to SPEC.md.
