# B-021: Can't lasso individual content inside an expanded section — the whole frame gets selected instead

**Status**: Fixed — confirmed on-device, closed via CR-007

## Symptom

While a section is expanded, trying to lasso even a small piece of
content inside the zone instead selects the entire mask/frame (the
`GEO_polygon` rings + border rectangle drawn to visually box and hide
the expanded area) — the actual content the user wanted to select
never gets picked, making it effectively impossible to lasso-select
inside an expanded section's zone at all.

## Root cause (confirmed on-device)

The mask's whole job is to be a solid-looking fill covering the entire
zone (REQ-230: hide anything underneath). Since the SDK can't draw a
true filled shape, `maskHelpers.ts` fakes it with many overlapping
thick-stroked concentric rings — real ink, densely covering the *whole*
interior, by design, no gaps. A lasso drawn anywhere inside the zone is
physically crossing that ink no matter where it's drawn, so it always
also selects the mask. Confirmed by testing with only the mask rings
present (no border): still happens. This isn't a shape/bounding-box
problem — reshaping the mask's pieces doesn't reduce how much of the
interior has real ink on it, since full coverage is the mask's entire
purpose.

## Approaches tried and ruled out

1. **4 line segments instead of 1 closed rectangle per ring/border**
   (original hypothesis). Refuted by the same-coverage argument above,
   confirmed by the border-removed on-device test.
2. **Replace the mask with native "erase" strokes** (idea: erase covers
   without adding selectable ink; back up covered content first,
   restore on recollapse). Investigated on-device:
   - Full erase deletes the stroke outright (0 elements remain).
   - Partial erase rewrites the stroke's geometry (new element, old one
     gone) — genuinely destructive either way, not a reversible overlay.
   - No stroke property distinguishes "erased" — the surviving stroke
     looks like an ordinary pen stroke. `eraseLineTrailNums` on it
     references an internal id with no corresponding element anywhere.
   - Tried inserting a stroke with `penType` 2–9 hoping one triggers
     erase behavior: all 8 rejected outright by the SDK itself
     (`error 302: "Invalid pen type"`). Only 1/10/11/14 (documented) and
     16 (seen on-device, undocumented) are valid pen types.
   - Conclusion: erasing is a native, gesture-only path-clipping
     operation with no programmatic equivalent in this SDK. Dead end.

## Breakthrough (confirmed on-device, 2026-09-24)

User's idea: what if a near-white **stroke** (not a `GEO_polygon`) is
treated by the SDK's rendering/hit-testing as effectively "erased" —
invisible on screen AND excluded from lasso hit-testing — while the
data itself is untouched (unlike real erasing, which is destructive)?

Confirmed by direct test: cloned a real stroke's exact geometry into a
new, separate, near-white (`0xFE`), much-thicker stroke drawn directly
on top of it.
- On screen: nothing visible (as expected for near-white ink).
- Selection: the covered original could not be lasso-selected **at
  all** — not "selectable but invisible," genuinely excluded.
- Data: still present and fully readable via `getElements` (confirmed
  via page dump) — not deleted, not mutated, a real non-destructive
  overlay.
- Decisive test: lassoed a region spanning **both** the white-covered
  area **and** a separate, real, visible stroke together → only the
  real stroke got selected. The white-covered area was completely
  excluded from the selection, exactly the behavior needed.

Working theory: `GEO_polygon` hit-testing uses the shape's full
bounding box regardless of visible ink (why the current mask rings —
and the border — get swept in wholesale); `STROKE` hit-testing appears
to work off actual rendered pixels, and near-white pixels apparently
don't count as "ink" for that purpose. This would mean switching the
mask's **fill** from `GEO_polygon` rings to near-white strokes fixes
the reported symptom directly.

**Open question before implementing:** the border (`createBorderRectangle`)
must stay visible (black) to show the section boundary, so it can't be
made near-white. Still need to confirm whether a black, thin,
rectangle-shaped **stroke** (as opposed to today's `GEO_polygon`
border) avoids the same "whole-bounding-box selected" problem — i.e.
whether the fix is specifically about color, or more generally about
`STROKE` vs `GEO_polygon` hit-testing precision regardless of color.

Border-as-stroke check also done: a hand-drawn closed stroke shape
does not sweep in content lassoed inside it — confirms the fix applies
to both the fill and the border.

## Next step

Escalated to CR-007 (`CRS/CR-007.md`) — fixing this establishes a new,
previously-unspecified guarantee ("content inside an expanded section
stays lasso-selectable"), so it's going through Change Request →
Feature to get a formal `REQ-NNN`, rather than bug-investigation's
lighter fast-track. This bug file stays open until CR-007's
implementation lands and is confirmed, then closes per
bug-lifecycle.md step 3. Diagnostic instrumentation
(`dumpPageProbe`/`whiteStrokeMaskProbe` in `src/index.ts`, currently
disabled but not yet removed) will be cleaned up as part of that
implementation.
