# B-006: Name reverts to its pre-move position after Expand → Collapse → move → Expand

**Status**: Fixed — confirmed by the user on-device (2026-07-14/15), and
further exercised without recurrence through everything built on top of it
since (underline feature, live redraw, icon glyph toggle). See DECISIONS.md
2026-07-14 "Name auto-follow: removed the heuristic instead of patching it
again" for the final fix (removed `nameSyncedRect`/`nameFollowDelta`
entirely rather than patching the heuristic a third time).

## Symptom
1. Create a section (Collapse).
2. Name it.
3. Expand it.
4. Collapse it (Recollapse).
5. Move the icon and/or the name while collapsed (exact composition/order not
   yet pinned down — one combined drag vs. two separate drags is unconfirmed).
6. Expand again — the name is repositioned back to where it was **before**
   step 5, undoing the user's move rather than following the icon or staying
   where they put it.

## Hypothesis
Traced `nameSyncedRect`/`nameFollowDelta` (`nameAction.ts`) end-to-end through
this exact sequence (`expandAction.ts`'s expand-time reconciliation,
`recollapseAction.ts`'s recollapse) and could not find a point where
`nameSyncedRect` goes stale for this particular sequence — recollapse carries
it forward untouched, and expand only updates it when the icon actually
moved. The expected outcomes I can derive from the code are either "name
follows the icon's delta" or "name is left exactly where the user put it" —
neither matches "reverted to its pre-step-5 position," which is a third,
unexplained outcome. I don't have a confirmed root cause.

One thing that would matter a lot and I don't know yet: in step 5, did you
do **one** drag that grabbed icon+name together, or **two separate** drags
(icon alone, then name alone, or vice versa)? The code path (and the correct
behavior per spec) differs between those cases, so this would narrow things
down a lot before reaching for a device trace.
