# B-011: Ink drawn over an expanded section's icon gets absorbed and can end up covering the icon (fixed)

**Status**: Fixed — confirmed by the user on-device (build `r122-content-shift`).

## Symptom
1. Section is expanded; user draws ink overlapping or encircling the icon.
2. Recollapse absorbs that ink as section content (intended — absorption
   itself was never the problem, confirmed with the user early on).
3. On the next Expand, the restored content/frame could end up covering the
   icon, making it hard to select for the next Recollapse.

## Root Cause
The section's area (content bbox + margin) is always grown to fully contain
absorbed content. When that growth reaches or surrounds the icon's own
position, nothing stopped the area from covering it — `stretchZoneToIcon`
only handled an icon *outside* the content, stretching the zone to reach it,
never an icon that ended up *inside*.

## Fix (two iterations before landing correctly — see DECISIONS.md 2026-07-20)
1. First attempt shrank the zone to stop at the icon's edge — fixed the
   overlap but visually cut real content out of the frame (confirmed
   on-device).
2. Second attempt translated only the zone rect, leaving strokes at their
   original positions — fixed the shrink, but a rectangle translated to
   clear a *nested* icon (e.g. ink circling it) can no longer contain that
   ink's bbox either (confirmed on-device with an encircling stroke).
3. Final fix: when the area would cover the icon, shift the **entire
   content** (not just the zone) as one rigid group, via a new one-time
   `CollapseSection.contentShift` field consumed at the next Expand. Every
   stroke's position relative to the others is preserved exactly (uniform
   translation); only positions relative to the icon change, which the user
   confirmed is correct — that relationship is only meaningful when driven
   by an explicit icon drag while expanded, not by incidental absorption.
