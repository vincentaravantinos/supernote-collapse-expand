# B-020: Content drawn after Expand gets wrongly protected from absorb once a resize happens

**Status**: Fixed — confirmed on-device

## Symptom

1. Expand a section.
2. Draw new strokes inside the expanded area.
3. Move the icon to resize the section (live-redraw).

The strokes from step 2 are then treated as "preserved" (protected,
not absorbable) instead of staying absorbable — the next Recollapse
should fold them into the section (per SPEC.md REQ-200, "new content
drawn on top of an expanded section is absorbed"), but after a resize
happens in between, it won't.

## Hypothesis (fairly confident — code-derived, not yet confirmed on-device)

This is a gap in CR-006's incremental `preservedNums` growth
(`iconMoveRedraw.ts::redrawSectionBox`, added 2026-09-22). At each
resize, the code adds any untagged, not-yet-preserved element whose
bbox overlaps the **new** (post-resize) zone to `preservedNums` — but
it never checks whether that element already overlapped the **old**
(pre-resize) zone. Content drawn after Expand, sitting inside the zone
the whole time (never itself the reason for a zone-shape change), gets
swept into "preserved" by the very next resize regardless, since the
check only asks "does it overlap the current zone," not "did the zone
just grow to newly cover it."

**Likely fix (not yet implemented):** also compute the *old* zone rect
(from `base.iconRect`/`base.relativeRect`, the section's shape just
before this redraw) and only add an element to `preservedNums` if its
bbox overlaps the *new* zone **and did not** already overlap the *old*
zone — i.e. genuinely newly-covered by this resize, not merely
still-present content that happened to already be inside.

## Next step

Fixed: `redrawSectionBox` now compares against the section's zone
*before* this resize, not just the new one — an element overlapping
both isn't "newly covered," so it stays out of `preservedNums`. A
follow-on visual issue found during testing (such content would still
briefly disappear under the freshly-redrawn mask, since it wasn't
reinserted on top of it) was fixed in the same pass: this content is
now also merged into the redraw's own reinsert step, tagged `CE_PART`
immediately rather than waiting for an actual Recollapse (see
DECISIONS.md 2026-09-25). Added REQ-240 to SPEC.md. Confirmed
on-device: the original repro, plus both CR-006 regression scenarios
(resize-over-pre-existing-content stays hidden-not-absorbed;
reshape-then-drag-in gets absorbed).
