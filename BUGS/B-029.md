# B-029: Tapping a button in a plugin dialog leaves a stroke on the page

**Status**: Parked

## Symptom

Tapping an option in any of the plugin's dialogs (e.g. "Collapse all
sections") leaves a stroke on the page underneath. The user saw the same in
the symbol_definition plugin.

## Hypothesis

symbol_definition's B-026/B-036: pen taps on *native* dialogs leak through
as ink; moving those messages into the plugin's own view fixed it there (and
our dialogs already are in the plugin view). So the leak here is likely
tied to our own view's behavior at the moment of the tap: answering a
dialog synchronously swaps the card from the (larger) dialog to the
(smaller) "Working…" card, or closes the view, exactly as the pen lifts. If
the native "don't draw under the plugin view" protection follows the view's
current layout/visibility, the tail of the pen contact lands on an
unprotected spot and is drawn as ink. symbol_definition's message flow
kept the card on screen until after dismissal.

## Evidence

User report. symbol_definition B-026/B-036/B-063 and DECISIONS.md
2026-07-22 (pen and touch are independent input layers; native
"disable drawing under this view" registration tied to the plugin view).

## Instrumentation

None yet.

## Next step

Not reproducible on the user's retry (2026-09-29). If it recurs, note: which
dialog and button, where the stroke landed (under the button? dot or line?),
pen or finger, and pull logcat right away. Candidate fix if the hypothesis
holds: keep the dialog card on screen ~300 ms after a tap before swapping
or closing it.
